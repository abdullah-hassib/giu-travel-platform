# Administration booking reads (ACC-17)

GET /api/admin/bookings requires an active administrator session with any mandatory password change completed. Type may be hotel or flight; omission combines both domains before one global sort, page and count. All responses are no-store and return data/meta, ten rows per page. The former unavailable-flight/combined 503 gate is removed now that the actual flight schema is integrated.

Optional filters are status, from, to and page. Dates filter hotel check-in or outbound flight departure local calendar date inclusively. Malformed/reversed ranges, unsupported state/type, operators, extra fields and unsafe page values return 400. Guests receive 401; travelers and both moderator roles receive 403. Inactive and restricted administrators remain denied.

Rows contain id/type, nullable reference, user/provider identities, dates, authoritative amount/currency, effective status and createdAt. Hotel identities remain the saved guest/provider snapshots. Flight owner display names use the actual user collection, projecting only fullName inside the lookup; a missing user shows Deleted user. Flight provider identity is the saved outbound airline. Flight dates run from outbound local departure date to final arrival UTC date. Round trips are one booking/amount/reference. Pending/expired private HOLD markers are not returned.

The service uses positive read projections of the actual HotelBooking and FlightBooking schemas and one aggregation union/facet. Newest createdAt sorts first, followed by type and ID for stable cross-collection ties, even if two domains share an ID. Private passenger/identity/birth-date/contact/security data, payment links, policies, hold timestamps, rooms/child details and arbitrary stored fields are omitted. Expiry and completion are derived for display/filtering without writing booking state, releasing inventory or touching payments. Flight completion waits for the final segment arrival; hotel date semantics are preserved. Authentication may renew its own session normally.

Swagger demo: log in as an admin, list without type to see both domains, then filter explicitly by flight/hotel, status and start-date range and request page 2. Empty domain/page results are valid 200 responses with consistent totals.

The actual HTTP/MongoDB tests retain existing hotel coverage and add globally interleaved pages/counts, cross-domain ID ties, flight privacy/owner lookup, inclusive local-date filtering, final-segment completion, no booking mutations and both moderator-role denials. Complete-AppModule smoke now verifies both domain and combined reads. Tests use disposable databases/configuration and no private environment/shared/external payment resource.

Typecheck, build, lint and 209 unit tests passed. Four targeted suites passed all 99 HTTP/database cases; the fresh remaining run passed 488 cases: 587 total across 23 suites.

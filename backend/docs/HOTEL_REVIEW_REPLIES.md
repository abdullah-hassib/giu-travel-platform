# Hotel moderator review replies - HTL-26 bonus

The user approved implementing one optional feature after the mandatory backend release. The official workbook's HTL-26 allows a hotel moderator to reply to a review. This slice extends MK's existing reviews with an optional embedded hotel response and reuses Hassib's current moderator assignment registry. Existing rating, booking, payment, review editing/deletion and moderation behavior is preserved.

## API

`POST /api/reviews/:id/reply` requires an active hotel moderator session, completed temporary-password change, and a current hotel assignment. The review must be visible and belong to that assigned active hotel. Administrators, travelers and airline moderators cannot reply through this endpoint. An unassigned/wrong-provider moderator receives 403; missing, hidden, deleted, inactive-hotel and cross-hotel targets receive 404.

Body:

```json
{ "comment": "Thank you for staying with us. We appreciate your feedback." }
```

Text is trimmed, required and limited to 1,000 characters. The cap matches review comments and is an implementation choice, not an additional official HTL-26 rule. Request and persistence validation use matching Unicode length semantics. Empty/null/non-string/oversized input, malformed IDs and extra fields such as moderatorId, createdAt or rating receive 400.

Success returns 201, Cache-Control: no-store, and only `{ comment, createdAt }`. The timestamp and moderator identity are generated by the server. One reply is supported per review; subsequent submissions return 409 without overwriting the original. The conditional single-document write allows exactly one concurrent submission to win. Reply editing/deletion endpoints are outside this slice.

`GET /api/hotels/:id/reviews` and existing create/edit review responses now include additive `reply: { comment, createdAt } | null`. Legacy reviews need no migration. Public responses omit the stored moderator ID and contact/account fields. Reply creation does not alter the guest comment, rating, hotel rating sum/count or review creation order. Guest edits preserve the hotel response. Existing guest anonymization still applies, while the response remains attributed to the hotel. Hiding a review hides its response; deleting the review removes the embedded response automatically.

The new request, response and nullable public-review field are documented in Swagger. All 110 mandatory PDF operations remain unchanged; this adds one optional operation. No new dependencies, shared seed, existing-data rewrite or external credential are needed. GEN-01's specified notification triggers do not include review replies, so no additional notification/event contract is introduced.

## Swagger demo

1. Log in as an assigned hotel moderator and complete any required password change.
2. Find an existing visible review through `GET /api/hotels/:id/reviews`.
3. Send the reply body to `POST /api/reviews/:id/reply`; expect 201.
4. Read the public review list and verify the hotel response appears while its rating is unchanged. A second reply receives 409, and a moderator from another hotel receives 404.

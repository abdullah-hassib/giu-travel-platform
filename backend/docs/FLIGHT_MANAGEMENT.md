# Flight schedule, cabin and cancellation management

Mandatory FLT-04/05/06/30 with PAY-03 and GEN-01/07. All mutations require an active, unrestricted airline-moderator account assigned to that exact airline. Guests and other roles are denied; a different airline assignment cannot edit/cancel the flight. Only future Scheduled flights may change; a passed departure is treated as Departed without allowing resurrection through an edit.

- PATCH /api/flights/:id accepts departureAirportCode, arrivalAirportCode, departureLocalDateTime and arrivalLocalDateTime. Supplied times use the selected official airport's local IANA zone and the existing DST/date validation. Omitted times preserve UTC instants. The airports must differ and arrival must follow a future departure. Airports are fixed after any booking, including expired/cancelled history. A duplicate flight number/airline/new-local-date is rejected. Empty, null, unknown or invalid fields fail validation.
- Active Pending Payment/Confirmed booking segments follow the updated schedule in the same transaction; cancelled/expired history retains its booked dates. Prices, passenger fares, baggage and cancellation policy snapshots remain frozen. Changes that would put an active round-trip return before outbound arrival fail with 409. Confirmed owners receive a real flight.schedule_changed notification; pending owners do not receive a manufactured confirmation/schedule notification. Identical time/airport requests do not emit another update.
- POST /api/flights/:id/cabins adds one unused category from Economy, Premium Economy, Business or First, using the same validated seat/fare/baggage inputs as creation. Held/booked counters start at zero. Duplicate categories are rejected.
- PATCH /api/flights/:id/cabins/:cabinId changes price and/or totalSeats. The stable cabin identifier is its fixed category (URL-encode spaces, e.g. Premium%20Economy); no cabin-ID database migration is introduced. Capacity cannot go below held plus booked seats. Edits and concurrent holds serialize through the flight write, preserving this invariant. Existing quotes retain their saved price; new holds use the changed fare. Clients cannot overwrite inventory counters.
- POST /api/flights/:id/cancel requires { confirmed: true } and returns 200 with flight/cancelledBookings/expiredHolds. In one retrying transaction it marks the own Scheduled flight Cancelled, expires/releases its pending whole-booking holds, cancels all its Confirmed whole bookings, releases every booked segment, reserves full provider-cancellation refunds through the actual RefundsService and saves notification/audit effects. Round trips remain one booking/refund, including when the other segment belongs to another provider; that other flight stays Scheduled. Existing user-cancellation tiers do not reduce the provider-cancellation refund. Repeat/departed cancellations are rejected without another refund.

No external Stripe request is made inside these transactions. Existing refund/reconciliation workers submit the reserved refund after commit. A racing signed success either confirms before cancellation and is then fully refunded as a provider cancellation, or sees an Expired hold and follows the approved full late-payment compensation. It never keeps a Confirmed booking on a Cancelled flight or releases seats twice. Failed refund/outbox persistence rolls the business state back. Queued refund status is reported truthfully; a reserved refund is not described as a completed live refund.

Actual Omar consumers deliver per-booking flight.cancelled notifications with the booking reference and audit the flight action. Per-booking envelopes preserve separate affected bookings for the same owner; the flight-level audit action is recorded once. Schedule/provider batches reuse the existing bounded outbox handoff. All administrative effects are visible in the canonical immediate/durable history and no event contains passenger identities, credentials or card data.

The real HTTP/replica-set suite covers schedule propagation/notifications and quote preservation, airport-history locks, fixed cabin uniqueness, capacity/fare edits, malformed/null/counter inputs, assignment/state/confirmation guards, active round-trip validity, cross-provider cancellation/full refunds/hold expiry, rollback on refund failure, and cancellation/payment plus capacity/hold races. Gateway requests alone use controlled responses; signatures and database transactions are real. No private environment/shared database/live gateway operation is used.

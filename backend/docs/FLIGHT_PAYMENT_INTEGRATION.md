# Flight foundation, booking and payment integration

This slice integrates Adham's submitted creation, time-zone and passenger-pricing work with the current official reference service, administration, payments/refunds and Omar's real event delivery. Hassib approved FLIGHT_INTEGRATION_PLAN.md before the shared model changes. Flight search, editing/cancellation of an entire flight, itinerary flight search, administrator combined pages and the required exports are subsequent slices; their absence is not represented as completed functionality.

## Airline and flight creation

An administrator creates an airline using POST /api/airlines with name, code and logoUrl. The obsolete moderatorId input is rejected: create the provider first, then POST /api/admin/moderators with airline_moderator and its providerId. The existing transactional moderator_assignments collection is the authority for exactly one provider per moderator. Temporary-password and account-status restrictions remain enforced. Assigned moderators can edit their profile and PUT baggage/cancellation policies; cross-provider attempts fail.

POST /api/flights accepts the submitted local-time/IATA/cabin inputs. It reuses ReferenceDataService and the verified official source instead of introducing a second airport seed or ObjectId airport collection. Airport IDs stored on flights are IATA strings. Adham's Luxon utility rejects invalid IANA zones, nonexistent/ambiguous DST times, invalid dates, identical airports, arrival before departure and past departures; duplicate flight number/airline/local-date and duplicate cabins are rejected. Cabins use the four official categories and integer USD cents. Baggage policy extraBagPrice is USD per bag and is converted into integer cents in booking snapshots.

Required admin provider deactivate/reactivate routes now accept airline as well as hotel. Airline transitions fence holds/flight creation, emit an audit event, notify assigned moderators and current upcoming Confirmed booking owners, and preserve paid reservations. Repeated commands produce no new transition. Hotel services/producers remain unchanged. New airline creation/profile/policy and flight-creation audit events are visible immediately in the canonical action history with pending delivery, then deduplicate against the durable audit copy after delivery.

## Booking and settlement

- POST /api/flight-bookings reviews a server-calculated summary without holding seats. POST /api/flight-bookings/hold atomically reserves the same shape for ten minutes. Both require a traveler session. Inputs are flightId, cabinCategory, passengers and optional returnFlightId/returnCabinCategory. A return flight must reverse the route and depart after outbound arrival.
- Passengers supply fullName, dateOfBirth, identityDocumentNumber and optional extraBags. When bags are selected, extraBagWeightsKg must contain one valid weight per bag within that segment's cabin limit. Passenger type is derived from the birth date at each departure; an optional supplied passengerType must match the outbound date. Adults/children occupy seats, infants pay ten percent without a seat, at least one adult is required and infants cannot outnumber adults. Return pricing/seats are calculated independently for that departure date.
- Hold creation uses retrying MongoDB transactions, provider fences and conditional cabin writes. All segments commit together or none do. The saved price, passengers, outbound cancellation tiers and per-segment baggage policies remain immutable for payment/cancellation; changing the live airline policies does not alter a held booking's quote.
- Existing GET /api/bookings/flight/:id/policies, POST .../accept-policies, payment create/retry/status and raw signed webhooks now use the concrete FlightPaymentAdapter. Only verified payment success consumes held seats into booked seats and generates the unique FLT reference. A repeated signature/event cannot confirm or consume twice.
- A five-second bounded expiry worker releases unpaid expired holds, including those without any payment record. Reads/new holds also run expiry reconciliation. Booking state changes first inside the release transaction so a competing worker/payment cannot release twice. A successful payment arriving after expiry cannot take replacement inventory; existing payment recovery reserves a full late-payment refund.
- GET /api/flight-bookings lists only owned bookings, with optional Upcoming/Past/Cancelled group and ten-row database pagination. GET /api/flight-bookings/:id returns private passengers, saved policies, status and cancellation preview. Completion is derived after the last segment's arrival. Foreign bookings return 404.
- POST /api/flight-bookings/:id/cancel confirms cancellation of the whole Confirmed booking before outbound departure. It releases all booked seats, changes state, reserves one saved-policy refund and emits the cancellation event in the same transaction. The applicable tier is the highest threshold not exceeding complete 24-hour days until outbound departure; no tier means zero percent. The refund applies to the whole paid total and rounds to integer cents. Repeat/late/foreign attempts are rejected; failure to reserve the authorized refund rolls everything back.
- Account deactivation now checks current/upcoming Confirmed flight segments as well as hotel stays. The existing user/payment fence serializes a racing deactivation and verified confirmation: confirmation wins and deactivation is blocked, or deactivation wins and the pending payment is recovered/refunded at normal hold expiry.

Actual flight confirmation/cancellation and airline provider events use Omar's durable outbox consumer. The existing refund consumer handles flight refunds. Producer sessions, effects and acknowledgment are transactional; unique event/recipient IDs prevent duplicate notifications. Bounded event batches support more than one hundred affected recipients without rejecting the business transaction or creating multiple audit actions. Queues/audit records remain retained.

## Verification and demo

Typecheck, build, lint and all 209 unit tests passed. Fresh sequential HTTP/database runs passed 32 flight integration plus 22 hotel/payment integration cases and 500 remaining cases: 554 total across 23 suites. Includes actual provider/assignment/reference integration, concurrent holds/expiry, SDK-signed settlement, round-trip cancellation/refunds, account/payment races, affected-party delivery, immediate/durable audit history and 101-recipient delivery. Only external Stripe responses are controlled; no private environment or shared/live payment resource was used.

Tests use actual modules, guards, validated DTOs, official reference seeding in a disposable local replica set and real Stripe SDK signature verification. External Stripe requests alone use controlled responses. Legacy airline/flight mock suites that assumed the conflicting moderator/airport models are replaced by real HTTP/database scenarios; the existing official reference source/seed/HTTP suite remains preserved. Adham's independent time-zone, pricing and booking-schema validation tests remain, with fixtures adapted to the canonical saved snapshot.

Swagger is at http://localhost:3000/api/docs when the app is running. Create airline → provision moderator → change temporary password → configure policies → create flight → review summary → hold → review/accept policies → create payment. A Confirmed reference requires a verified gateway event; clients cannot submit a successful-payment claim. Use the owned detail's refundPreview before cancellation.

The submitted booking-reference unique index is preserved without changing its options. Pending records use a private HOLD marker, hidden by the public projection and replaced by the actual FLT reference only after verified settlement. No shared index migration is introduced.

Private live Stripe test credentials remain unconfigured. Local controlled-gateway tests do not prove live Stripe acceptance. No shared database migration/seed, private .env inspection or live payment/refund operation is performed by this slice.

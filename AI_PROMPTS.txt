Date: 2026-11-15
Student: Hassib
Tool: Codex
Related requirements: ACC-06, ACC-19; preserves ACC-04/ACC-08 authentication behavior
Prompt / request (summary): Implement the approved opaque access/refresh-cookie authentication design, rotation/replay protection, revocation, legacy-session transition, Swagger and real-database tests; handle version control.
How the output was used: Created feature/auth-refresh-rotation from current develop. Login sets giu_session and giu_refresh HttpOnly/SameSite cookies. Access lifetime is an implementation choice of five minutes, bounded by the original absolute deadline. Refresh credentials combine a random family secret and rotating secret; only family and credential hashes persist. Atomic rotation replaces both credentials. Consumed-token replay and concurrent reuse revoke the family. Frontends must serialize refresh across tabs and require login after refresh rejection or uncertain replay. Logout accepts either cookie and clears both; password changes and inactive account/version checks invalidate both. Added POST /api/auth/refresh, sanitized Swagger response schemas, both cookie security schemes and no-store authentication responses. Preserved existing routes and legacy single-cookie sessions within their original absolute/idle limits until re-login. Updated README, API conventions and implementation status. No teammate-owned modules or secrets were touched.
Verification: npm run typecheck, npm run build and npm run lint passed. Nine unit suites / 35 tests and three e2e suites / 49 tests passed. Twenty-two e2e cases used real disposable MongoDB 8.2.7, including the real HTTP login/protected-request/refresh/logout flow. Other HTTP cases use service/guard mocks; production Secure/HttpOnly/SameSite flags are asserted. No shared Atlas or .env access. No new dependencies in this slice.
Remaining limits: Local HTTP development deliberately uses non-Secure cookies; Secure is enabled for production and direct HTTPS. Live HTTPS browser and Atlas verification remain pending. Legacy sessions do not gain refresh capability without re-login. Admin-assisted password reset and mandatory first-login changes, complete profile fields, booking-aware deactivation and remaining authorization/integration work are subsequent slices.
